# Crop-IT

**Live app:** <https://crop-it-frontend.onrender.com> 
**Backend API:** <https://crop-it-backend.onrender.com>

A machine learning crop recommendation system: given soil chemistry (N, P, K, pH) and climate conditions (temperature, humidity, rainfall), it recommends the most suitable crop using a real scikit-learn classifier trained on the real [Kaggle Crop Recommendation Dataset](https://www.kaggle.com/datasets/atharvaingle/crop-recommendation-dataset).

Every prediction, metric, correlation, PCA projection, cluster, and confusion matrix shown in the app is computed from that real dataset and real trained models — nothing in the live prediction/analytics path is hardcoded or simulated.

## Project Overview

Crop-IT has three parts:

1. **A Python ML backend** (`python_backend/`) that loads the real dataset, trains three scikit-learn classifiers, evaluates them, and serves predictions and analytics through a FastAPI service.
2. **An Express gateway** (`server.ts`) that proxies the React frontend's `/api/*` calls to that FastAPI service, with no fallback to fake data if the Python service is unavailable.
3. **A React/TypeScript frontend** (`src/`) — crop recommendation form, model performance dashboard, dataset analysis, and unsupervised (K-Means/PCA) analysis pages.

This system was built incrementally, phase by phase, replacing an earlier prototype's hardcoded TypeScript "ML engine" with a real, trained, evaluated pipeline. That legacy code has been removed; see [Limitations](#limitations) for what the real system does and does not claim.

## Dataset

- **File:** `data/Crop_recommendation.csv`
- **Rows:** 2,200
- **Columns:** `N, P, K, temperature, humidity, ph, rainfall, label` (7 features + 1 target)
- **Classes:** 22 crops, perfectly balanced at 100 samples each (apple, banana, blackgram, chickpea, coconut, coffee, cotton, grapes, jute, kidneybeans, lentil, maize, mango, mothbeans, mungbean, muskmelon, orange, papaya, pigeonpeas, pomegranate, rice, watermelon)
- **Missing values:** 0
- **Duplicate rows:** 0
- **Source:** [Kaggle — Crop Recommendation Dataset](https://www.kaggle.com/datasets/atharvaingle/crop-recommendation-dataset) (see [Dataset Provenance](#dataset-provenance))

The dataset file is never modified, sampled, or regenerated by any part of this codebase. `python_backend/app/data_loader.py` validates it on every load (correct columns, numeric types, no missing/infinite values, at least 2 classes) and raises immediately if it doesn't match — it never silently repairs bad data.

## ML Pipeline

The full pipeline lives in `python_backend/app/`:

| Module | Responsibility |
|---|---|
| `config.py` | Paths (resolved from `__file__`, not cwd), feature/target schema, `TEST_SIZE=0.20`, `RANDOM_STATE=42` |
| `data_loader.py` | Loads and validates the real CSV; raises on any structural problem |
| `preprocessing.py` | Stratified train/test split; builds unfit `StandardScaler` pipelines |
| `train.py` | Trains all 3 models, cross-validates, evaluates, selects a model, saves artifacts |
| `predictor.py` | Loads saved artifacts once; serves predictions, metrics, model-info, confusion matrices, feature importance |
| `analysis.py` | Real-time correlation, PCA, and K-Means computed from the dataset |
| `schemas.py` | Pydantic request/response models (mirrors the frontend's TypeScript contracts) |
| `main.py` | FastAPI app wiring all of the above into HTTP endpoints |

## Models

Three real scikit-learn classifiers, each a full `Pipeline` (so the saved artifact always includes whatever preprocessing it needs):

| Model | Pipeline | Configuration |
|---|---|---|
| Random Forest | `Pipeline([("model", RandomForestClassifier)])` — no scaling (scale-invariant) | `n_estimators=300, random_state=42, n_jobs=-1` |
| K-Nearest Neighbors | `Pipeline([("scaler", StandardScaler), ("model", KNeighborsClassifier)])` | `n_neighbors=5` |
| Support Vector Machine | `Pipeline([("scaler", StandardScaler), ("model", SVC)])` | `kernel="rbf", probability=True, random_state=42` |

## Preprocessing

Leakage-prevention contract, enforced by construction (see `preprocessing.py` and `train.py`):

```
CSV → validate → stratified train/test split → fit StandardScaler on TRAIN ONLY
    → transform train → transform test
```

`StandardScaler` is a pipeline step for KNN/SVM, so cross-validation refits it fresh on each fold's training portion — it never sees validation or test data during fitting.

## Training

Run with `python -m app.train` from `python_backend/`. It:

1. Loads and validates the real CSV
2. Splits 80/20, stratified on the 22-class target, `random_state=42`
3. Builds the three model pipelines
4. Cross-validates each (5-fold `StratifiedKFold`, `shuffle=True`, `random_state=42`) on the **training split only**
5. Fits each pipeline on the full training split
6. Evaluates each on the **untouched test split**
7. Selects a model — see [Evaluation](#evaluation) for the criterion
8. Saves `models/random_forest.joblib`, `knn.joblib`, `svm.joblib`, `best_model.joblib`, and `model_metadata.json`

Training is deterministic (`random_state=42` throughout) — rerunning it reproduces the same split, the same cross-validation folds, and (barring library-version drift) the same metrics.

## Evaluation

**Model selection criterion** (documented in code, in `model_metadata.json`, and applied automatically — never a hardcoded "best" model):
- **Primary:** cross-validation macro-F1 mean, computed on the training split only
- **Secondary (tie-break):** cross-validation macro-F1 standard deviation, lower is better, applied only when scores are within `1e-4` of each other

**Actual results from the last training run** (`python_backend/models/model_metadata.json`, `sklearn==1.5.2`, `python==3.11.9`, train=1,760 / test=440):

| Model | Test Accuracy | Test Macro F1 | Test Weighted F1 | CV Accuracy (train only) | CV Macro F1 (train only) |
|---|---|---|---|---|---|
| **Random Forest** ✅ selected | 99.32% | 99.32% | 99.32% | 99.38% ± 0.55% | **99.37% ± 0.56%** |
| SVM (RBF) | 98.41% | 98.40% | 98.40% | 97.90% ± 1.03% | 97.88% ± 1.06% |
| KNN (k=5) | 97.95% | 97.93% | 97.93% | 96.53% ± 1.21% | 96.50% ± 1.24% |

Random Forest was selected because its CV macro-F1 mean (99.37%) is not within `1e-4` of any other model's — a clean, non-tied win. Test-set metrics are reported for transparency but played no role in selection, per the project's non-negotiable rule against test-set leakage into model choice.

These are the actual numbers computed on this machine's last training run; retraining (see [Retraining](#retraining)) may shift them slightly if scikit-learn's version changes, but the methodology and selection process will not.

## API Endpoints

Served by FastAPI (`python_backend/app/main.py`). Express (`server.ts`) proxies most of these to the frontend at the same path; `/api/correlation` and `/api/pca` are Python-only (Express merges both into `/api/visualizations` for the browser — see below).

| Method | Path | Reachable via Express? | Real, computed from |
|---|---|---|---|
| GET | `/api/health` | ✅ same path | Whether all model artifacts loaded successfully |
| POST | `/api/predict` | ✅ same path | The saved best model's `.predict()` / `.predict_proba()` |
| GET | `/api/metrics` | ✅ same path | `model_metadata.json` (Phase 4 training run) |
| GET | `/api/model-info` | ✅ same path | `model_metadata.json` (schema, class names, training timestamp) |
| GET | `/api/dataset-summary` | ✅ same path | The real CSV, loaded and computed per request |
| GET | `/api/correlation` | ⚠️ via `/api/visualizations` | `df[FEATURES].corr()` on the real CSV |
| GET | `/api/pca` | ⚠️ via `/api/visualizations` | `StandardScaler` + `PCA(n_components=2)` on the real CSV |
| GET | `/api/clusters` | ✅ same path (also aliased at `/api/unsupervised-analysis`) | `StandardScaler` + `KMeans` (K=2..10, selected by max silhouette) |
| GET | `/api/confusion-matrix` | ✅ same path | The real per-model test-set confusion matrices saved during training |
| GET | `/api/feature-importance` | ✅ same path | The saved Random Forest's `feature_importances_` |
| GET | `/api/python-code` | ✅ same path | The actual `train.py`/`main.py` files, read live from disk |

`/api/clusters` is the most CPU-intensive route (K-Means across K=2..10, each with an O(n²) silhouette-score pass over 2,200 samples) — Express proxies it with a 30s timeout rather than the default 8s, since it measured ~10.5s on a free-tier deployment's shared CPU vs. ~1.3s on a fast dev machine.

`POST /api/predict` request body:
```json
{ "N": 90, "P": 42, "K": 43, "temperature": 20.9, "humidity": 82.0, "ph": 6.5, "rainfall": 203.0 }
```
Response includes the real prediction (`recommendedCrop`, `probability`, `alternatives`, `modelComparison` across all three models), plus two clearly-separate, non-ML enrichments merged in by Express: `inputAnalysis` (threshold categorization of the submitted values) and `cropProfile` (static botanical reference facts — scientific name, season, description — for whichever crop the real model recommended). Neither enrichment affects the prediction.

If the Python backend is not configured (`PYTHON_BACKEND_URL` unset) or unreachable, every one of these routes returns a real `503` — there is no fallback to fake data anywhere in this path.

## Frontend Integration

- `src/services/api.ts` — typed `fetch` wrappers for every endpoint above, with timeout handling and honest error classification (network failure vs. validation failure vs. backend-down)
- `src/types/ml.ts` — TypeScript types kept in sync with the actual FastAPI response shapes (see `python_backend/app/schemas.py`)
- Pages: `Recommendation.tsx` (prediction form), `ModelPerformance.tsx` + `MetricCharts.tsx` + `ConfusionMatrix.tsx` (real metrics/confusion matrix), `DatasetAnalysis.tsx` + `CorrelationHeatmap.tsx` + `PcaPlot.tsx` (real dataset stats/correlation/PCA), `UnsupervisedAnalysis.tsx` + `ElbowChart.tsx` (real K-Means)
- Every page shows an explicit error state (with instructions to start the Python service) when the backend is unavailable — never a silent fallback

## Environment Variables

| Variable | Where | Purpose |
|---|---|---|
| `PYTHON_BACKEND_URL` | Express (`server.ts`) | URL of the FastAPI service, e.g. `http://localhost:8000`. Required for any `/api/*` route to return real data. |
| `VITE_API_BASE_URL` | React (build-time) | Optional: point the frontend directly at a different API base URL instead of same-origin `/api`. |
| `FRONTEND_ORIGIN` | FastAPI (`python_backend/app/main.py`) | CORS allow-origin for the frontend dev server. Defaults to `http://localhost:3000`. |

Copy `.env.example` to `.env.local` and fill in as needed (the example file also documents two unrelated `GEMINI_API_KEY`/`APP_URL` variables left over from the original project scaffold — they are unused by this application).

## Running Locally

**Terminal 1 — Python ML backend:**
```bash
cd python_backend
uvicorn app.main:app --reload --port 8000
```

**Terminal 2 — Express + React (from the repo root):**
```bash
PYTHON_BACKEND_URL=http://localhost:8000 npm run dev
```

Then open the app (default `http://localhost:3000`), go to **Crop Recommendation**, and submit a real prediction. **Model Performance**, **Dataset Analysis**, and **Unsupervised Analysis** all pull live from the endpoints above.

## Retraining

To retrain on the (unchanged) real dataset and regenerate `python_backend/models/`:
```bash
cd python_backend
python -m app.train
```
This is deterministic (`random_state=42`) and will overwrite the committed artifacts with a freshly trained, freshly evaluated set. Commit the updated `models/` directory (including `model_metadata.json`) if you want the new run's numbers reflected in this README and the running app.

## Deployment

**Live deployment** (Render, free plan):
-  **App:** <https://crop-it-frontend.onrender.com>
-  **Backend API (direct):** <https://crop-it-backend.onrender.com>

Deployed via the `render.yaml` Blueprint below, with no service-name collision — both services got their predicted URLs on the first deploy. Fully verified working end-to-end against the live URLs above: `/api/health`, a real `POST /api/predict` (correct crop, real model comparison, real `inputAnalysis`/`cropProfile` enrichment), `/api/metrics`, `/api/dataset-summary`, invalid-input `400`, `/api/correlation`, `/api/pca` (both via `/api/visualizations`), `/api/clusters`, `/api/confusion-matrix`, and `/api/feature-importance` — all returning real, correct data through the deployed frontend proxy, confirmed by re-checking the live site after each fix below.

Two real issues this surfaced, both fixed and confirmed live:
- **Server-side:** `/api/clusters` (K-Means across K=2..10, each with an O(n²) silhouette-score pass) took ~11s on Render's free-tier shared CPU, longer than Express's default 8s proxy timeout — Express was misreporting a slow-but-working backend as "unreachable". Fixed by giving that one route a 30s timeout in `server.ts`.
- **Client-side:** the browser's own fetch for that same route (`fetchClusters`/`fetchUnsupervisedAnalysis` in `src/services/api.ts`) had the same 8s default, so the Unsupervised Analysis page kept showing "ML Backend Unavailable" even after the server-side fix. Fixed by raising it to 35s there too — confirmed by checking the deployed JS bundle hash matches the build that includes this fix.

`render.yaml` (repo root) is a [Render Blueprint](https://render.com/docs/blueprint-spec) that deploys both services together:

- **`crop-it-backend`** — the Python/FastAPI ML service (`rootDir: python_backend`), `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- **`crop-it-frontend`** — the Express gateway + React SPA, `npm ci --include=dev && npm run build` then `npm run start`

**To deploy your own copy:** in the Render dashboard, **New → Blueprint**, connect your fork of this repository. Render detects `render.yaml` and provisions both services on its free plan.

**One-time step after the first deploy:** Render assigns each service a URL of the form `https://<name>.onrender.com`, unless that name is already taken elsewhere on Render (in which case it appends a random suffix). `render.yaml` assumes no collision and pre-fills `FRONTEND_ORIGIN` / `PYTHON_BACKEND_URL` accordingly. After the first deploy, confirm each service's real URL in the dashboard; if either differs from the guess, update the *other* service's corresponding env var and redeploy that one service.

Notes:
- The committed `python_backend/models/*.joblib` and `model_metadata.json` deploy as-is — the build does **not** retrain. To ship a freshly retrained model, retrain locally (see [Retraining](#retraining)), commit the updated `models/`, then redeploy.
- `data/Crop_recommendation.csv` is committed, so the backend's dataset-dependent endpoints work immediately without any extra upload step.
- The browser only ever talks to `crop-it-frontend`; its Express gateway calls `crop-it-backend` server-to-server (not subject to browser CORS), so `FRONTEND_ORIGIN` mainly matters if you point `VITE_API_BASE_URL` at the backend directly instead of going through the gateway.
- Render's free plan spins services down after inactivity — the first request after idling will be slow (cold start).
- For any other host (Docker, a VPS, etc.), the same two commands apply: run the FastAPI service reachable by the gateway, and run `npm run build && npm run start` for the gateway with `PYTHON_BACKEND_URL` pointed at it.

## Limitations

- **Dataset scope:** the model is trained solely on the Kaggle Crop Recommendation Dataset (2,200 rows, 22 crops, India-centric agronomic ranges). Its accuracy reflects how well it separates *these* 22 classes on *this* dataset's feature distributions — it is not validated against real farm outcomes, other geographies, or crops outside this list.
- **No claim of real-world agronomic accuracy:** a 99.32% test accuracy describes performance on a held-out split of this specific dataset, not a guarantee about real soil/field conditions.
- **K-Means found K=2, not a larger "nicer" number of clusters.** Selecting K by maximum silhouette score across K=2..10 on the real data genuinely produces K=2 (silhouette ≈0.417) — a 2000-vs-200-sample split — rather than a more narratively appealing K=4. This is reported as-is rather than forced to look tidier.
- **PCA's first two components explain ~46% of total variance** (PC1 ≈27.6%, PC2 ≈18.5%), computed on the real dataset. The 2D scatter plots are a partial, not complete, view of the 7-dimensional feature space.
- **Confusion-matrix "similar features" explanations** are a real, computed heuristic (smallest normalized difference between two classes' per-feature means) — a plausibility signal, not a rigorous causal analysis of why any specific sample was misclassified.
- **No hyperparameter tuning** beyond the initial reasonable configuration documented above — per project scope, this was intentionally not over-engineered.
- **Static crop reference data** (`server/cropReference.ts`: scientific name, season, description) is hand-curated general agronomic knowledge, not derived from the dataset or any model, and is clearly separated from the ML prediction path.
